# ML-Dive: Debugging prompt for IBM Bob 2.0

## Context

Target log: `logs/train_log.csv`
Format: `iteration, epoch, train_loss, val_loss, lr, timestamp`
Length: 5000 iterations, 100 epochs, 50 iterations per epoch.
Generated by `logs/generate_logs.py` — the script intentionally injects four classes of anomalies.

## Scenario

A training run has just finished. The metrics look wrong somewhere but the engineer does not know where to start. She has the CSV and access to the training code (Detectron2 fork). She needs a triage report: what went wrong, when, and what to change.

## Steps

### Step 1 — Plan mode: define the analysis

Switch Bob to **Plan** mode. Ask it to lay out an analysis plan:

- what to check first (loss, then lr, then cross-check)
- how to segment the log into epochs
- what counts as an anomaly for each metric
- which checks can run in parallel

Do not read the log yet — just design the plan.

### Step 2 — Agent mode: read and summarise the log

Switch to **Agent** mode. Ask Bob to:

1. Load the CSV.
2. Report: number of rows, epoch range, iteration range, which columns are numeric.
3. Print the first 5 and last 5 rows.
4. Report min / max / mean for `train_loss`, `val_loss`, `lr` (ignoring rows where loss is not a number).

### Step 3 — Subagents: detect each anomaly class in parallel

Spawn four subagents, one per anomaly class:

**Subagent A — NaN / Inf detection**
- Find every row where `train_loss` or `val_loss` is not a finite number.
- Report the first iteration and epoch where it appears.
- Count total NaN rows and how many epochs are affected.

**Subagent B — Loss spike detection**
- Compute the rolling median of `train_loss` (window = 10 iterations).
- Flag any iteration where `train_loss` exceeds 3x the rolling median.
- Report the top 5 spikes with iteration, epoch, value, and ratio to median.

**Subagent C — Overfitting detection**
- For each epoch, compute mean `train_loss` and mean `val_loss`.
- Look for any window of at least 5 consecutive epochs where mean `train_loss` decreases while mean `val_loss` increases.
- Report the window, the slope of each curve, and the widening gap.

**Subagent D — Learning-rate / plateau detection**
- Track `lr` over epochs. Report every change point.
- Find any window of at least 10 consecutive epochs where `lr` is constant AND mean `train_loss` changes by less than 1%.

Collect all four reports.

### Step 4 — Consolidate

Back in Agent mode, ask Bob to:

- Merge the four subagent reports into one table.
- For each anomaly, give: name, epoch range, evidence (numbers), severity (high / medium / low).
- Sort by severity.

### Step 5 — Suggest fixes

For each anomaly, ask Bob to propose concrete fixes, grounded in the Detectron2 codebase. For each fix:

- what to change (file + parameter, if known)
- why this should help
- how to verify after the change (what to look for in the next run)

Example directions (Bob should confirm against the repo, not assume):
- NaN loss → check LR, gradient clipping, AMP settings, data pipeline for NaN inputs.
- Loss spike → check batch size, warmup schedule, gradient norm.
- Overfitting → early stopping, augmentation, dropout, weight decay, smaller model.
- Stalled LR → check scheduler config, step size, plateau detection.

### Step 6 — Produce the triage report

Ask Bob to output a single markdown file `TRIAGE_REPORT.md`:

- one-paragraph executive summary
- anomaly table (from Step 4)
- for each anomaly: evidence + suggested fix + verification step
- "what to run next" — one concrete command or config change the engineer should try first

## Output format

- Markdown.
- All numbers formatted to 4 decimal places.
- Cite iteration / epoch for every claim.
- No emojis, no motivational filler.
- If Bob cannot confirm a fix against the repo, mark it as "hypothesis — verify in repo".

## Success criteria

An ML engineer who has never seen this log can, after reading the report, (a) name every anomaly, (b) point to the exact epoch and iteration, and (c) make one concrete change to the training config to address the most severe issue.
